# Realty Labz — Project Guide for Claude Code

## Overview
Realty Labz is a web application built for real estate agents (starting with Michigan) to manage their business finances, mileage/tax deductions, and client documents in one place. It launched as an individual-agent tool and is now formally expanding into a multi-tenant SaaS platform — individual agents, teams, and brokerages/offices as first-class account types, with role-based permissions (Broker, Admin, Team Lead, Agent) and complete data separation between organizations. See "Platform Expansion Roadmap" below for the phased plan.

**Founder context:** Built by a working Michigan realtor who wants a lean, low-cost MVP first, with an eye toward pitching this to their brokerage for team-wide use later — the Platform Expansion Roadmap below is that pitch made concrete.

**Long-term direction:** the goal is for Realty Labz to grow into a one-stop shop for an agent's entire business and financial life — personal finances, investments and other assets, clients, listings, and contracts, not just business income/expense bookkeeping. See "Long-Term Vision" below. V1 stays scoped to the business-finance core defined in the roadmap; this broader direction should inform architecture decisions (e.g., keep data models extensible rather than assuming "only business transactions" will ever exist) without pulling future scope forward into the current build.

## Design & Quality Bar (read this before building anything)
This is the top priority of the project, alongside cost-consciousness — **the app should feel like it was designed by Apple.** That means:
- Clean, minimal, uncluttered UI. Generous whitespace. Restrained color palette. No visual noise.
- Careful typography, spacing, and alignment — details are not "polish for later," they're the product.
- Every interaction should feel obvious and frictionless — no confusing flows, no dead ends, no unnecessary steps or fields.
- Smooth, subtle motion/transitions (state changes, loading states, page transitions) — never jarring, never gratuitous.
- Consistency: the same component, spacing scale, and interaction pattern used everywhere it applies. No one-off styling.
- Prefer removing a feature/field/step over shipping it half-considered. Simplicity and clarity beat feature count.
- When a UI decision is ambiguous, default to the simpler, calmer option.
- This bar applies from the first screen built (auth/onboarding) — do not plan to "add polish later."

## Tech Stack
- **Frontend + Backend:** Next.js (App Router) — this **is** React; there's no separate frontend framework decision to make.
- **Database:** PostgreSQL, hosted on Supabase. Prisma is still the ORM/query layer (via `@prisma/adapter-pg`, see `src/lib/db.ts`) — Supabase here means "hosted Postgres + storage," not the Supabase client/SDK for data access.
- **File storage:** Supabase Storage (private `documents` bucket) — see `src/lib/document-storage.ts` and `src/lib/supabase.ts`. Replaced local disk storage; see "Current Status" for the migration note.
- **Hosting:** Vercel
- **Version Control:** GitHub
- **Auth:** NextAuth.js (Auth.js v5), JWT session strategy (no adapter/DB sessions needed). Deliberately **not** Supabase Auth — decided 2026-07-16 to keep the already-working NextAuth flow rather than rewrite it; Supabase is DB + storage only here. Two providers as of 2026-07-21: **Credentials** (email + password, the v1 default) and **Google** (added on direct founder request — see Current Status for how account linking/creation works).
- **UI:** Tailwind CSS + a small set of consistent, accessible primitives (e.g. shadcn/ui as a base) — favor a restrained design system over ad-hoc styling, in service of the Apple-like quality bar above.
- **Crypto wallet balances:** three free, public, no-API-key-required endpoints — mempool.space (Bitcoin balance), Hiro's Stacks API `api.hiro.so` (STX balance), CoinGecko's `simple/price` endpoint (USD conversion). See `src/lib/wallet-balance.ts`. On-demand only (fetched on add + a manual "Refresh" button) — no scheduled/cron polling, keeping this at zero infra cost and within the free tiers' rate limits.
- **Fillable/signable PDF forms:** `pdf-lib` (reads page sizes, draws filled-in values/signatures onto a PDF, appends the certificate-of-completion page — server-side only) + `pdfjs-dist` (renders PDF pages to `<canvas>` client-side, for both the template field-designer and the public fill/sign page) + `react-signature-canvas` (signature capture, **pinned to `1.0.7`** — a bare `npm install` resolves to a `1.1.0-alpha.2` prerelease because that's the package's `latest` dist-tag, which isn't actually the newest stable release; same stability-over-bleeding-edge reasoning as the recharts pin below). See Current Status (2026-07-22 Forms entry) for the full design.
- **Transactional email:** `resend` — used for the Forms e-signature request/completion emails (`src/lib/email.ts`). `RESEND_API_KEY` + a verified `realtylabz.com` sending domain configured 2026-07-23 (`RESEND_FROM_EMAIL="Realty Labz <notifications@realtylabz.com>"`) — see Current Status.
- **Charts:** `recharts`, pinned to **`2.15.4`** — deliberately not the latest major (`3.9.2`), which has a confirmed real regression: a `Pie` with more than one slice renders the second-and-later slices at roughly half their correct angle, leaving a visible gap in the ring (reproduced, isolated down to the raw SVG arc path recharts generated, and fixed by downgrading — not a CSS/layout issue on this app's side). Don't bump past the 2.x line without re-testing a multi-slice donut chart first. Theme colors for charts are `--chart-1` through `--chart-6` in `src/app/globals.css` (light/dark pairs, same pattern as `--accent`/`--danger`/etc.) — reference them via `var(--chart-N)`, don't hardcode hex in chart components.
- **Tests:** `vitest` (added 2026-07-26), `npm test` — unit tests for every calculation that touches real dollar amounts (loan amortization, mileage deduction, home office deduction, deal net-commission, budget usage, recurring due-date advancement, CSV parsing, estimated tax). `vitest.config.ts` mirrors `tsconfig.json`'s `@/*` path alias. Deliberately no React/component tests yet — the value has been in catching wrong math, not rendering, and live Playwright passes cover the UI wiring.
- **CSV parsing:** `papaparse` (added 2026-07-26, for bank-statement import on `/finances/import`) — hand-rolling a CSV splitter breaks on quoted fields with embedded commas, which real bank exports have.

## Architecture Principles
- Keep infrastructure costs near zero until the app has proven traction.
- Build with a `users` → `teams` relationship from day one (roles: `agent`, `team_lead`, `admin`), even though v1 only needs individual-agent functionality. Do not hardcode single-user assumptions.
- Web-first, fully responsive — no native mobile or desktop app for v1. Mobile wrapping (React Native/Expo) is a possible future phase, not now.
- Michigan-only tax/mileage rules for v1. Store state-specific rates/rules (e.g., mileage deduction rate) in a config/table that's easy to update annually and easy to extend to other states later — not hardcoded in logic.
- **Multi-tenant data isolation is enforced in application code, not database RLS.** Because auth stays on NextAuth (not Supabase Auth — see Tech Stack), Postgres Row-Level Security keyed to `auth.uid()` isn't available to us. Every query touching tenant-scoped data (transactions, deals, documents, clients, templates, etc.) **must** filter by the owning `userId` and/or `teamId` explicitly in the Prisma call — the same pattern already used in every `src/app/actions/*.ts` file (e.g. `deleteMany({ where: { id, userId } })`). This is the load-bearing security boundary for the whole multi-tenant platform; treat any query missing that scoping as a bug, not a style nit.
- **Team = tenant/organization**, regardless of size. A `Team` row represents anything from a 2-agent team to a full brokerage — there is deliberately no separate "Brokerage/Office" model layered above `Team`. Simpler data model, avoids premature nesting; revisit only if a real customer needs teams-within-a-brokerage.
- **Personal financial data is never team-visible, full stop — no exceptions for managers.** `Asset` (personal investments) and `Transaction` rows scoped `PERSONAL` are queried by plain `userId` only (see `src/lib/finance-data.ts`), never through `teamOrOwnFilter`/`teamSharedFilter`. Every other team-aware model in this app gives managers (`TEAM_LEAD`/`ADMIN`/`BROKER`) some form of wider visibility; this is the one deliberate exception, because personal finances aren't the business's data to see even for a broker. Don't "fix" this by adding manager visibility later without an explicit founder decision — it's not an oversight.

## Core Data Model (initial draft)
- **users** — agent accounts, auth info, role, team_id (nullable for solo agents)
- **teams** — optional grouping for brokerages/team features (v2 activation); also the multi-tenant unit — see Architecture Principles ("Team = tenant/organization")
- **clients** — belongs to a user; contact info, notes
- **properties/listings** — optional, tied to clients
- **transactions** — income/expenses; `scope` (BUSINESS/PERSONAL, added 2026-07-20) + category field (mileage, home office, phone, other — business-only, nullable); tied to user
- **mileage_logs** — trip records: date, distance (miles, manually entered), business/personal flag, note (e.g. client name/purpose), calculated deduction amount (rate × miles at time of trip)
- **documents** — contracts/PDFs; tied to client and/or user; supports e-mail-a-link-to-client flow for client-filled info (v2)
- **assets** — personal investments/other assets (added 2026-07-20): name, type (stocks/retirement/real estate/crypto/savings/other), current value (manually updated by default, no history log), tied to user only — **never** team-visible regardless of role, see Architecture Principles. Crypto-type assets can optionally link a Bitcoin or Stacks wallet address instead of a manual value — see Current Status entry on wallet balance tracking.
- **loans** — personal debt tracking (added 2026-07-20): mortgages, auto loans, and other installment debt in one model (`type`: MORTGAGE/AUTO/OTHER). Purchase price, down payment, interest rate, term, start date, annual property tax, annual insurance, and (MORTGAGE-only) an expected annual home-appreciation rate. Same personal-only, never-team-visible pattern as `assets`. Monthly payment, current principal/interest split, remaining balance, and payoff date are all computed on read from a simulated month-by-month schedule (`src/lib/loan-calculations.ts`), never stored — see Current Status.
- **loan_extra_payments** — one-off extra-principal payments a user logs against a loan (added 2026-07-20): date, amount, optional note. Applied at the month they fall in during the amortization simulation — pulls the payoff date earlier without changing the loan's required monthly payment, same as how extra payments work on a real fixed-rate loan.
- **form_templates / form_template_signers / form_fields / form_submissions / form_submission_signers / form_field_values** — the Forms/e-signature feature (added 2026-07-22, see Current Status). `FormTemplate` is the reusable PDF + its defined signer roles and fields; `FormSubmission` is one sent instance to specific signers (sequential, legally-binding-grade e-signature with a consent/IP/timestamp audit trail); the completed, flattened PDF becomes a normal `Document` row, reusing that model's storage/list/download plumbing rather than duplicating it.

**⚠️ Naming collision to plan around:** the existing `Transaction` model means an *income/expense ledger entry*. The Platform Expansion Roadmap's "Transaction Management" (Phase 2) means a *real estate deal* (buyer/seller side, timeline, deadlines, commission). These are different things that will both need to exist — when Phase 2 is built, the deal-tracking model needs its own name (e.g. `Deal` or `RealEstateTransaction`), not `Transaction`. Flagging now so it isn't a surprise later.

**Not yet in the schema, needed for Phase 2+ (see Platform Expansion Roadmap):**
- `Role` enum needs a `BROKER` value added (currently `AGENT` / `TEAM_LEAD` / `ADMIN`) to match the doc's Broker / Admin / Team Lead / Agent hierarchy.
- A deal-tracking model (see naming collision above): buyer/seller workflow state, timeline, deadlines, commission, shared team access.
- Reminder/notification records tied to deal deadlines (Phase 3).
- ~~Document template model for brokerage-level shared templates~~ — built as `DocumentTemplate` (2026-07-20, see Current Status). Auto-fill of office/agent info is not built — no office/license data exists in the schema yet, and this was deliberately deferred (see Current Status entry for why).

## Feature Roadmap

### V1 (MVP — build in this order)
1. **Authentication** — agent signup/login
2. **Dashboard** — light/dark mode toggle; at-a-glance view of income, expenses, mileage savings
3. **Expense & income tracking** — categorized (home office %, phone, vehicle, other business expenses) for tax purposes
4. **Mileage tracker (manual entry)** — user manually logs each trip: date, miles, business/personal flag, and a note field (e.g. "Showing to Joe Smith"); calculates deduction using current MI state mileage rate and shows dollar amount saved per trip. 5. **Client management** — basic client records (contact info)
6. **Document storage** — upload/store contracts and PDFs per client

**Key deliverable inside V1:** PDF export of financials for accountants — leads with net income/loss summary, then itemized breakdown by category showing how the numbers were calculated (mileage trips + rate, expense categories, etc.)

### Future — Native App Phase (not v1, not v2 — a distinct later phase)
- **Automatic, location-based mileage/trip detection** (background GPS logging, auto-classify business/personal) is explicitly deferred until the app is wrapped as a native app (React Native/Expo). Continuous background location tracking is not reliably achievable in a responsive web app (mobile browsers, especially iOS Safari, restrict background GPS access), so don't attempt to build this into the web app — manual entry is the correct v1 approach, not a stopgap to route around technically.
  - **Reaffirmed 2026-07-29** after the founder asked what a MileIQ-style tracker would take: a web-only "tap Start, GPS tracks while the tab's open, trips land in a review queue" version (using the browser Geolocation API, no native app needed) was proposed as a buildable middle-ground stepping stone — real tradeoff disclosed being that tracking pauses if the phone locks or the user switches apps mid-drive, unlike true background tracking. Founder chose to wait for the full native iOS app instead of building that intermediate web version. Don't propose the web-Geolocation stepping stone again without a new founder ask — this was a considered decision, not an oversight.

#### Phase 2 — Transaction Management, Broker/Office Dashboard, Team Management
Planned 2026-07-17. Decisions locked in during planning:
- **Team invites are shareable links, not real emails** — no transactional email provider yet (keeps cost/setup at zero for now). A manager generates a link with an expiring token; they send it themselves via whatever channel. **Pre-launch TODO:** once Vercel + Supabase are live, revisit this — at minimum the invite link needs a real base URL instead of `localhost:3000`, and real email delivery (e.g. Resend) is worth adding at that point instead of staying manual-link-only forever.
- **Deal deadlines are a flexible task list**, not fixed fields (inspection/financing/closing hardcoded on the deal itself) — a generic `label` + `dueDate` + `completedAt` per deadline, added freely per deal. Chosen specifically because Phase 3's automatic deadline detection and reminders need to create arbitrary deadlines, not just fill in three predetermined slots.
- **Team Lead has team-wide visibility**, same as Admin and Broker — all three see every deal/agent on the team; only Agent is scoped to their own. Practically, `TEAM_LEAD` / `ADMIN` / `BROKER` are one "manager tier" for data-access purposes in Phase 2 (a shared `isManager(role)` check), even though they're separate enum values and may earn distinct capabilities later (e.g. billing, removing the team itself — not designed yet).
- **The whole feature is client-centric, per direct founder feedback 2026-07-18** — not "Deals as a disconnected flat list." A client's page shows their properties/offers (deals) and documents in one place — mirrors the actual job: organize through clients → properties → offers → contingencies, so the app removes work instead of adding a parallel system to babysit. This is why `/clients/[id]` exists (a detail page, not just an inline-edit list) and why every agent — not just managers — gets their own upcoming-contingencies view on `/dashboard`; deadline visibility is for "them and myself," not just the broker.

**New data models needed** (none of these exist yet):
- `Role` enum gains `BROKER` (currently `AGENT` / `TEAM_LEAD` / `ADMIN`).
- `Deal` — the buyer/seller transaction/workflow itself. Fields: `side` (BUYER/SELLER/DUAL), `status` (ACTIVE/UNDER_CONTRACT/PENDING/CLOSED/FELL_THROUGH), `propertyAddress`, `mlsNumber`, `listPrice`, `salePrice`, `commissionRate`, `commissionAmount`, `closingDate`, `notes`. Scoped by `userId` (the assigned agent) exactly like every other model — **not** a `teamId` field; team-wide visibility for managers is a query-time join through `user.teamId`, not stored redundantly on the deal. Optionally linked to an existing `Client`. This is the model that resolves the naming collision noted under Core Data Model — it is explicitly **not** named `Transaction`.
- `DealDeadline` — the flexible task list per the decision above: `label`, `dueDate`, `completedAt` (nullable — set when done), belongs to a `Deal`.
- `Document.dealId` (new nullable field, same pattern as the existing `Document.clientId`) — so contracts can be tied to a deal.
- `TeamInvite` — `teamId`, `role` (what the invitee becomes), `expiresAt`, `usedAt` (nullable), `createdBy`. Built simpler than originally planned: no separate `token` field — `id` (already an unguessable cuid) doubles as the invite link's token, matching the pattern every other model here uses (`/api/documents/[id]`, etc.), so `/join/[id]` is the link.

## Current Status
- **Full-app audit + "billion-dollar-ready" build: 2 real security bugs fixed, 2 critical CVEs patched, plus 4 new CRM/competitive features (2026-07-29/30, direct founder request: "analyze this web app so far. make sure it is a fully maxed out web app that is the perfect tool for a real estate business. Review a plan and lets build better to execute on and make a billion dollar project.")**. Planned via `EnterPlanMode` after three parallel audit agents (feature-completeness vs. the roadmap and real competitors like SkySlope/kvCORE/Follow Up Boss; UX/design-consistency vs. this app's own Apple-like bar; security/tenant-isolation/tech-debt) surveyed the real codebase, not just this doc's self-reported status — every finding below was personally spot-verified (read the actual code, or reproduced the actual bug) before being trusted. Two follow-up questions were asked before building anything: which of four cheap "Tier 2" features to prioritize (founder chose **all four**) and whether to scope any of the big-ticket "Tier 3" items now (founder chose **hold off on all of it**, staying cost-conscious per this app's founding principle).
  - **Two real, exploitable cross-tenant (IDOR) bugs found and fixed** — both the same shape: a server action verified the user owns a *parent* record, then mutated a *child* record using only its own id, never cross-checking the child actually belongs to that verified parent. `src/app/actions/deal-deadlines.ts`'s `toggleDeadlineAction`/`deleteDeadlineAction` verified `dealId` ownership via `assertDealAccess`, then ran `dealDeadline.update`/`.delete` scoped by `id` alone — any user who owned/managed *any* deal could pass an arbitrary deadline `id` from a different tenant and mutate/delete it. `src/app/actions/form-templates.ts`'s `deleteTemplateSignerAction` had the identical gap one function over from `saveFormFieldsAction`, which already cross-checked its ids correctly in the same file. Both fixed by switching to `updateMany`/`deleteMany` with a compound `where: { id, dealId }` (or `{ id, formTemplateId }`), matching the safe pattern `loan-extra-payments.ts` already used. **Verified live, not just read**: seeded two real tenants, used the real UI's own delete/toggle forms with the child id forged via `page.evaluate()` to point at the other tenant's row (dealId/templateId left correctly pointing at the attacker's own — the exact exploit path), confirmed the victim's row survived the forged request both times, and confirmed the legitimate same-tenant delete/toggle paths still work unchanged.
  - **Two dependencies with known, currently-open CVEs, patched with a same-minor safe bump**: `next-auth`/`@auth/core` `5.0.0-beta.31` → `5.0.0-beta.32` (was carrying two **critical** CVEs — an auth existence-check that can fail open under misconfiguration, and an email-normalizer Unicode-homoglyph bypass — confirmed both gone via `npm audit` after the bump) and `next` `16.2.10` → `16.2.12` (a **high**-severity middleware/proxy-bypass issue specifically under Turbopack, this project's exact build config). A remaining high-severity `sharp`/`postcss` finding is bundled *inside* Next.js itself (not a direct dependency of this project) and no stable Next release yet resolves it without `npm audit fix --force` downgrading to the ancient `next@9.3.3` — correctly left alone rather than "fixed" into a broken app. Verified live: Credentials and Google sign-in both still work post-bump, a real Google OAuth screen still resolves with no config error.
  - **Small honest bugs/polish fixed alongside**: the downloaded PDF report's filename still said `realty-labs-financial-summary-*.pdf` (one-line fix — a leftover from the 2026-07-19 rename that missed this one spot); the landing page's tagline and root `<meta name="description">` were still stuck describing V1 scope (finances/mileage/documents only) despite Deals, e-signature Forms, Team dashboards, and full personal finance all shipping since — refreshed to describe what's actually built, the single highest-leverage fix given the founder's own stated brokerage-pitch goal; Account page's three forms (`profile-form.tsx`/`password-form.tsx`/`invite-form.tsx`) used the secondary (outlined) button variant for their only/primary action, unlike every other full-page form in the app — switched to primary for consistency; added a root `src/app/global-error.tsx` (with its own minimal `<html>`/`<body>`, since Next.js requires that for errors above the root layout) so an error thrown above the `(app)`/`(auth)` route groups gets a branded boundary instead of Next's raw default.
  - **Client-facing portal** (`ClientPortalSession` model, `src/lib/client-portal.ts`, `src/app/actions/client-portal.ts`, `/portal`, `/portal/[token]`, `/api/portal/documents/[id]`) — a magic-link session, deliberately **not** a NextAuth/User account (a `Client` isn't part of the Role/team model at all). An agent's "Send portal access" button on the client detail page (`forms/[id]/page.tsx`) creates a session row and emails the link via the existing Resend setup; visiting `/portal/[token]` sets an HttpOnly cookie holding *only* the opaque session id, never a clientId. Local dev and production intentionally share this one project (decided 2026-07-16) — no separate dev database, so there's one connection story instead of "local now, something else at deploy time." What's actually in `.env.local`:
  - `DATABASE_URL` — the **transaction pooler** connection (port `6543`, `?pgbouncer=true`). This is what the running app uses for every normal query via `src/lib/db.ts`.
  - `DIRECT_URL` — the **session pooler** connection (port `5432`, same host, no `pgbouncer` flag). Despite the name, this is *not* a literal direct-to-Postgres connection — Supabase's own Prisma-connect flow generates it this way and explicitly labels it "used for migrations." Session mode (unlike transaction mode) supports the prepared statements/advisory locks Prisma Migrate needs.
  - **Resolved, not just worked around:** Prisma 7 permanently removed `datasource.directUrl` from both `schema.prisma` and `prisma.config.ts` (confirmed via Prisma's own docs, 2026-07-20 — not a gap waiting on a future release). The datasource config only ever takes a single `url`. So `DIRECT_URL` is never read automatically — running a migration means temporarily pointing `DATABASE_URL` at the `DIRECT_URL` value for that one command, e.g. (POSIX shell): `DATABASE_URL="$DIRECT_URL" npx prisma migrate deploy`. `.env.local`'s real `DATABASE_URL` (the pooler) is untouched by this — it's an inline override for a single command, not a file edit.
  - `SUPABASE_URL` — the **base project URL** (`https://mwnadqbmrrtepcjoihwi.supabase.co`), *not* the REST endpoint (`.../rest/v1/`) shown on the Data API integration page — the `@supabase/supabase-js` client appends `/rest/v1/`, `/storage/v1/`, etc. itself. Passing the REST-suffixed URL breaks Storage calls specifically, which this app depends on for documents.
  - `SUPABASE_SERVICE_ROLE_KEY` — Supabase has renamed this key type; new projects show a **secret key** (prefixed `sb_secret_...`) rather than the older JWT-style `service_role` key, but it's the same role/purpose. Don't confuse it with the **publishable key** (`sb_publishable_...`, the new name for the old `anon` key) — that one doesn't have the permissions this app's server-side storage code needs.
